## 踩过的坑（省下重复调试时间）

- **本机编译极慢**（单次 1-5 分钟），且**前台命令超时被 SIGTERM 会杀死 rustc 子进程**，
  留下损坏中间产物 → 后续报 "only metadata stub found" 之类假错误。
  **长任务一律 `run_in_background: true`**；怀疑中毒就换干净的 `CARGO_TARGET_DIR`。
- **多子代理并行编译会互相拖慢/OOM**（16 核 / 13.7GB）→ 让每个子代理加 `-j 1` 并串行化。
- **子代理偶发"重复粘贴"整段代码** → 产生 `E0428 name defined multiple times`。
  slice009 的仓储就有一整段重复（含 `Bind`/`non_blank`/常量），已清理。
- **子代理会误用不存在的 API**。已知两处真实误用：
  - `rust_decimal::Decimal` **没有** `ceil_dp` / `to_i32`。要向上取整用
    `round_dp_with_strategy(n, RoundingStrategy::ToPositiveInfinity)`；
    要取整数值需 `use rust_decimal::prelude::ToPrimitive;` 才有 `to_i64()`。
  - `tigshop_core::Error::forbidden` 不存在（用 `Error::biz(code, msg)` 或 `Error::Forbidden`）。
  - 子代理还可能 `use rand::`（该 crate 未声明依赖）→ 用 `tigshop_common::utils::random_hex()`。
  **在 prompt 里预先写死这些约束能显著减少返工。**
- **切片文件写进 `crates/core/src/models/` 时不能用 `tigshop_core::` 前缀**（它就是 core 自己），
  要用 `crate::`。slice003 的 models 文件犯过这个错。
- admin 侧 `routes/{catalog,shop,...}.rs` 里有**引导期内联实现**，与切片路由重复。
  合并切片时必须删除被接管的那些 `.route(...)`、其 handler、以及 `lib.rs`
  `implemented_routes()` 里的对应 base 行。本次已处理：
  - `admin/lib.rs`：删掉 product/order/adminUser 的内联路由与 handler；
  - `admin/routes/catalog.rs`：只保留 `category/getAllCategory` + `brand/list` 之外全删；
    后续又让 slice005 接管了 `brand/list`，故 catalog.rs 现只剩 `getAllCategory`。
  - `public/routes/shop.rs`：`/shop/shop/detail` 交给 slice013，本文件只留 `category/tree`。
- **public 侧两种约定并存**：早期域是 `public_routes()` / `authorized_routes()`（无状态），
  切片域是 `routes(state)` 且**自带鉴权中间件** → 切片一律 `merge_public`，外层不要再套 `require_auth`。
- `slice014` 的服务构造原本是 `new(repos, is_o2o)` 两参数，与其余切片不一致（导致注册工具无法识别）。

## ⚠️ 工具缺陷与一次"差点上线的真实缺陷"（务必读，别再踩）

### 1. `register_slices.py` 的三个静默失效（已修）
这三个都不会让编译失败，却会让**路由/状态长期不被注册**，是最危险的一类问题：

| 缺陷 | 后果 | 修法 |
|------|------|------|
| `reg_public` 漏写 `return self.touch(F_PUBLIC_LIB, fn)` | 函数返回 `None`，`apply_one` 视为"成功"却**什么都没做** → `PublicState` 里所有切片字段从未被写入 | 补回 return；并在 `apply_one` 里加防御：**任何注册点返回 `None` 即报错**（否则漏写 return 会永远静默） |
| `insert_in_block` 用**全文件级**幂等检查 | `AdminState`/`PublicState` 里 `sliceNNN: sliceNNN.clone(),` 文本完全相同 → 第二个块被误判"已存在"而**漏插**（slice021 的 public 字段就这样丢了） | 改成**块作用域**幂等检查（只在目标块内查找） |
| `reg_db_mod_repo` 用 `impl Repositories {` 作初始化项锚点 | 行被插到 `fn new` 收尾 `}` **之后**（块内但在 `Self { }` 字面量之外）→ 直接语法报错 | 锚点改为 `Self {`（该文件里唯一） |
| `reg_main` 用 `slice001: slice001.clone(),` 作 public 状态锚点 | 该行在 `AdminState`/`PublicState` **同时存在**，工具取第一个匹配 → public-only 切片被插进 `AdminState` | 锚点改为块起始行 `let public_state = PublicState {` |
| 无条件加 `pub mod sliceNNN;` 到 `core/src/models/mod.rs` | 有些切片不需要自己的 DTO（直接复用 `BatchDTO` 等）→ `E0583 file not found for module` | 仅在 `core/src/models/sliceNNN.rs` **真实存在**时才声明 |

### 3. `check_sql_columns.py` 的跨语句拼接误报（已修），以及它害我改错代码
旧实现从含 DML 关键字的行开始，一直收集到某行以 `"..."` 加 `,)]` 结尾为止。但仓储层大量
使用 `push_cond(...)` 这类**单行调用**（行尾是 `);` 而非 `",`），于是收集器**跨函数把多条 SQL
拼成一条**：`UPDATE decorate ...` 与后面 `pc_navigation` 查询的 `` `type` = ? `` / `title LIKE ?`
被合并，凭空产生「`decorate` 表不存在列 `type`」这类误报。

> **真实教训**：我照这条误报去"修"了 `paginate_navigations`（查 `pc_navigation`）里
> 本来正确的 `"title LIKE ?"`，改成 `"decorate_title LIKE ?"` —— 而 `pc_navigation`
> **没有** `decorate_title` 列，这会让该接口在**运行时**报 `Unknown column`。
> 已经回退并在此处留注释。**结论：校验器报错时，先确认它把 SQL 归属到了哪张表，
> 不要盲目照改。**

修法：改为按**调用/语句边界**切分（行尾 `;` / `);` / 字面量闭合即结束），并在遇到新的
DML 关键字字面量时另起一条。修完后扫描语句数从 529 增至 **618**，未知列 **0**。
