## 1. 执行摘要

### 结论

本源码是一套多模块、带运营后台及多端客户端的成熟电商系统，不是单纯的商品展示站。后端以 Java / Spring Boot 为主，前台包含 Nuxt 3 + Vue 3，管理后台为 Vue 3 + Vite，另有 UniApp 多端工程。数据库脚本、支付 SDK、消息队列、存储与多种业务模块表明，重写范围涉及完整交易和运营链路。

### 总体建议

采用“Rust 模块化单体 + 分阶段替换”的方式：Axum/Tokio 承接 API 与业务服务；Leptos 可作为新商城及后台的候选 UI 技术，但应先用关键页面做技术验证；SQLx 用于数据库访问。首期不建议微服务化，也不建议一开始就把所有前端、后台、移动端同时重写。

### 决策门槛

进入正式开发前，必须完成业务范围确认、支付/退款链路核验、生产配置与密钥治理、数据库表及数据保留策略确认，并以可运行的端到端原型验证 Rust 技术栈。

### 审计边界

本报告依据上传 ZIP 的目录、构建清单、配置文件名称、控制器命名、SQL 脚本与前端 `package.json` 做静态审计。未连接生产数据库、未访问第三方账户、未运行完整系统，也未逐个验证所有业务方法。因此，“已发现”指源码结构证据，“待验证”不代表功能一定可用或有缺陷。

## 2. 源码盘点与技术栈

### 后端工程

根目录为 Maven 多模块工程，采用 Java 21、Spring Boot 3.3.4。主要模块包含 `tigshop-api`、`tigshop-adminapi`、`tigshop-service`、`tigshop-bean`、`tigshop-common`、`tigshop-security`、`tigshop-feign`。源码约有 1,000 个量级的 Java 文件（具体数量以自动化统计为准）。

### API 入口

静态统计到前台 API 控制器约 69 个、管理 API 控制器约 176 个。控制器数量不等于接口数量；下一阶段应解析映射注解，输出 HTTP 方法、路径、权限、请求/响应结构及调用链。

### 商城前台

`view/Tigshop-Pc` 使用 Nuxt 3 / Vue 3，声明国际化、站点地图、Pinia、Element Plus、Ant Design Vue 等依赖；目录中有数百个 Vue 文件。构建脚本包含 production/test 环境构建和前端规则检查。

### 运营后台

`view/admin` 使用 Vue 3、Vite、TypeScript，依赖包括 Axios、Pinia、Element Plus、Ant Design Vue、ECharts、富文本编辑器与表格/拖拽相关组件；目录中有大量 Vue 页面与组件。

### 移动端

`view/uniapp` 是 UniApp / Vue 3 多端工程，声明 H5、Android/iOS App 及多个小程序平台构建脚本。若“全站”包含移动端，这部分必须独立纳入范围，不能默认由 Leptos 一次替代。

### 数据与部署

项目包含约 65 个 SQL 文件；初始化 SQL 中检测到多条 `CREATE TABLE` 语句。`docker-compose.yml` 声明容器服务/资源配置。配置与依赖显示 MySQL、Redis、RabbitMQ，以及对象存储、支付、短信、搜索等外部集成线索。

### 测试线索

本次按路径静态统计未发现常规 Java `src/test` 测试类。前端 `package.json` 声明部分 Vitest / type-check / lint 脚本，但是否有足够的有效测试、是否可通过，需在干净环境中执行并核验。

## 3. 业务能力地图（初步）

### 商品与目录

商品、SKU/规格、分类、品牌、商品属性、商品库存、批次、评价/晒单、商品分组、搜索及商品内容/装修。迁移时需明确商品状态、SKU 组合、库存口径、图片与附件引用、批量导入导出及 SEO 字段。

### 交易与售后

源码线索涉及订单、订单日志、购物车、促销、优惠券、秒杀/拼团等活动、售后、发票、订单配送等。应以真实接口与服务调用链核实具体业务规则，特别是订单状态转换、拆单、取消、退款、优惠分摊、运费与税费。

### B2B 批发

后台控制器命名中可见 wholesaler、wholesale setting、wholesale product、price inquiry 等模块。应把企业客户身份、最小起订量、阶梯价、询价/报价、批量下单列为核心验收场景。

### 多商户与财务

可见商户申请、商户账户、子商户、利润分成、提现、保证金、余额/流水等控制器命名。必须确认本项目实际启用哪些功能，以及平台、商户、供应商、销售人员之间的账务边界。资金相关数据不应在迁移时仅做简单表复制。

### 跨境与本地化

前端依赖与业务线索包含多语言/币种切换、海外支付、税务/发票、海外客服等。需逐项核实实际启用国家/地区、展示语言、结算币种、税费规则、汇率来源、时区、地址格式、隐私同意和数据保留要求。

### 权限与运营

存在管理用户、角色、权限、API Token、管理日志、报表/导出、运营面板、装修、消息/客服等线索。重写时必须保留按钮/菜单权限之外的服务端权限校验、数据范围限制与关键操作审计。

### 第三方能力

依赖清单中出现微信/支付宝相关 SDK、PayPal/Stripe 相关组件、云存储、短信/邮件、地图、搜索和 RabbitMQ 等技术线索。依赖存在不代表线上已启用；需按生产配置、代码调用点和商户账户逐项确认。

## 4. 风险评级与处理措施

### P0 — 凭据与环境配置

压缩包包含 `.env` 文件及生产环境配置文件路径。当前报告不复述其中的值。必须确认是否包含真实凭据；若有，立即轮换密码、Token、私钥及第三方密钥，并从后续发布包和版本控制中剔除。所有秘密改由部署密钥管理系统注入。

### P0 — 支付与账务正确性

支付回调、退款、分账/结算、余额与提现属于高风险域。迁移前要建立渠道清单、验签方式、幂等键、状态映射、对账流程和失败补偿策略；切换前进行沙箱与真实小额验证。

### P0 — 数据保留和迁移

即便允许新建数据库，也不能默认丢弃历史订单、支付流水、退款、售后、发票、商户账务和审计日志。先明确法律/财务保留要求、迁移范围、只读归档方案及回查方式。

### P1 — 业务覆盖遗漏

控制器、DTO、服务和前端页面数量较大，且存在商城、管理后台、移动端三类客户端。以文件数量估算工期不可靠；需产出接口清单、页面/菜单清单、角色矩阵和关键流程图。

### P1 — 跨境价格与税费

禁止使用浮点数作为货币金额。定义币种精度、舍入策略、税价含/未含税规则、运费、汇率来源和订单汇率快照。下单后保存商品、优惠、税、运费、币种与收货信息快照。

### P1 — 并发与一致性

库存预占、订单重复提交、支付通知重放、消息重复投递及退款重试均需幂等设计。采用数据库事务、唯一约束、状态机与可重试任务，避免库存超卖、重复入账或重复发货。

### P1 — 移动端范围

UniApp 包含多个目标平台脚本。Leptos 适用于 Web，但不是现有 UniApp 所有 App/小程序目标的直接替代。必须决定移动端保留、渐进迁移，还是单独重写。

### P2 — 可观测性与恢复

需补齐结构化日志、trace/request ID、指标、告警、备份恢复演练、发布回滚、数据修复操作留痕。不能把“服务能启动”视为上线标准。

## 5. 目标架构建议

### 总体模式

采用模块化单体优先：单一可部署后端，内部按领域划分 crate/module；通过清晰的接口与依赖规则隔离业务。只有在吞吐、团队协作或独立发布有明确证据时再拆分服务。

### 推荐技术

- **后端：** Rust stable、Tokio、Axum、Serde、SQLx、tracing。
- **数据库：** MySQL 保留与 PostgreSQL 重建之间设置决策门。
- **缓存：** Redis。
- **异步消息：** 首期可继续 RabbitMQ，避免同时重写消息基础设施。
- **前端：** Leptos SSR/CSR 作为候选，先验证复杂页面和组件成熟度。
- **外部服务：** 对象存储、搜索、支付、邮件与物流继续使用成熟服务，通过适配层集成。

### 数据库决策

虽然可重新建库，但应先完成原表与业务关系映射，再决定 MySQL 或 PostgreSQL。若现有 MySQL 数据和生态可复用，先保留 MySQL 可降低迁移风险；若决定 PostgreSQL，应安排 SQL 方言、索引、JSON、事务、排序规则和数据迁移专项。

### 前端迁移策略

先选商品列表/详情、登录、购物车、结算、订单中心和一个高复杂度后台模块制作 Leptos 验证原型。比较 SSR/SEO、表格编辑、表单校验、国际化、图表、富文本、拖拽装修及组件成熟度。若后台复杂交互成本过高，可先保留 Vue 管理后台，不必为“全 Rust”牺牲交付可靠性。

## 6. Rust 模块迁移对照表

| 旧系统领域 | 代码/业务线索 | Rust 建议模块 | 关键验收点 |
|---|---|---|---|

## 7. 可执行实施计划与阶段门

> 以下工期为初步规划区间，阶段可能并行，不能直接相加作为承诺总工期。需在审计收口和技术验证后建立基线计划。

### 阶段 0：审计收口（估算 1–2 周）

- 输出接口清单、页面/菜单清单、业务流程、支付/物流渠道表、表关系图、权限矩阵、部署拓扑与缺陷清单。
- 完成业务方访谈，确认实际销售市场与移动端范围。
- **阶段门：** P0 风险有负责人和关闭计划，功能范围由业务方确认。

### 阶段 1：技术验证（估算 2–3 周）

- 建立 Rust workspace。
- 实现健康检查、登录/授权、商品列表/详情、一个后台表格、SQLx 数据访问、结构化日志与 Docker 构建。
- 验证 SSR、国际化、关键组件、可访问性与性能。
- **阶段门：** 根据验证结果冻结 UI 与数据库路线。

### 阶段 2：基础域（估算 3–5 周）

- 身份、权限、媒体、分类、商品、SKU、定价与基础配置。
- 要求新旧接口对照与关键场景自动化测试。

### 阶段 3：交易核心（估算 4–8 周）

- 购物车、库存预占、订单状态机、优惠计算、支付适配层、回调幂等、退款与对账。
- **阶段门：** 通过并发库存、支付异常、退款及对账测试。

### 阶段 4：跨境与扩展业务（估算 3–6 周）

- 市场/语言/币种、税费/运费、物流、发票、B2B 阶梯价、商户和财务能力。
- 按业务方确认的真实启用范围实施。

### 阶段 5：前后台与移动端收口（估算 4–8 周）

- 完成商城主要页面、运营后台、报表、装修、客服及决定纳入范围的移动端。
- 后台高复杂度组件需根据阶段 1 验证结果调整路线。

### 阶段 6：迁移演练与灰度上线（估算 2–4 周）

- 数据抽取/清洗/校验、影子流量或只读对照、UAT、支付/退款/发货演练、回滚演练、监控与备份恢复验证。
- 按市场/用户分批切换。

## 8. 验收标准（上线阻断项）

- **功能对照：** 每个已启用的旧页面、API、后台菜单、权限、定时任务和第三方集成均有新实现，或有经业务方签字确认的退役决定。
- **交易正确性：** 订单总额、折扣、税费、运费、币种、退款金额在新旧系统对照测试中一致；支付回调重复提交不会重复入账；退款不会超过可退金额。
- **库存与幂等：** 并发压测下库存不超卖；重复下单、重复消息、重复支付回调和重复退款请求均得到安全处理；异常订单可追踪并可人工补偿。
- **权限与安全：** 未授权 API 返回拒绝；数据范围隔离通过测试；管理操作有审计记录；生产秘密不进入仓库/镜像/日志；依赖漏洞与安全配置完成评审。
- **跨境规则：** 按每个目标市场覆盖价格显示、结算币种、税费、运费、地址、语言、时区、发票/同意记录等测试用例。
- **可运维性：** 有监控告警、日志追踪、备份恢复演练、发布回滚步骤、故障处理手册和明确的值班责任人。
- **性能与稳定性：** 根据现有线上基线确定 SLO 和压测阈值；在没有业务峰值和基础设施数据前，不预设虚构的吞吐量或延迟指标。

## 10. 已知限制与需业务方确认的问题

### 审计限制

当前为静态源码审计，尚未成功构建/启动项目、连接数据库、执行端到端业务或访问第三方账户；因此不能判定生产系统运行状态、实际启用支付渠道、线上数据量或真实性能。

### 待确认问题

1. 哪些国家/地区是第一期目标市场？
2. B2B、多商户、O2O/门店、礼品卡、分销/销售员、余额/提现等功能哪些必须保留？
3. 移动端是否包含 App 与小程序？
4. 哪些历史数据必须迁移？
5. 生产支付/物流供应商有哪些？
6. 是否允许首期保留 Vue 管理后台或 UniApp，以降低交付风险？

### 最终建议

先完成 A1–A6 的业务与风险收口，再开展 A7 技术验证；验证通过后确定 Rust 目标架构、数据库路线、分阶段范围与团队计划。不要先生成大量 Rust 文件再反向补业务规则。
